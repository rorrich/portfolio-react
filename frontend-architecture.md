# Заметки по Frontend-архитектуре

Короткие правила проекта, чтобы не терять единый стиль.

## 0) Краткая карта проекта (где что хранится)

- `src/pages/*` — страницы приложения (роуты).
- `src/pages/CasePages/*` — кейс-страницы (`Roast`, `Cleanner`, `DrCoffee`).
- `src/components/*` — переиспользуемые UI-компоненты.
- `src/components/CaseComponents/*` — строительные блоки для кейсов (`CaseHero`, `CaseBlock`, `TextGroup`, `ImageGroup`).
- `src/context/*` — глобальные состояния/механики (`ThemeContext`, `PageTransitionContext`).
- `src/hooks/*` — пользовательские хуки с UI-логикой.
- `src/data/*` — данные/каталоги (например, `cases`).
- `src/types/*` — контракты данных и типы.
- `src/navigation/*` — конфиги навигации и правила активных роутов.
- `src/constants/*` — константы layout/роутов/порогов.
- `src/styles/*` — глобальные токены и базовые стили (`variables`, `base`, `utilities`).

## 1) Общие правила проекта

### 1.1 Структура страниц

- Все страницы лежат в `src/pages/*`.
- Для новой feature-страницы использовать папку уровня страницы (`<PageName>/<PageName>.tsx`), если там есть своя логика/стили.

### 1.2 Когда выносить subcomponents

Выносить локальный subcomponent только если:

- блок повторяется 2+ раза, или
- у блока есть собственная внутренняя логика, или
- файл страницы становится тяжело читать.

Если блок одноразовый и читается нормально inline, вынос не нужен.

### 1.3 Ответственность за стили

- Переиспользуемое поведение живет в module-стилях компонентов.
- Уникальный визуал конкретной страницы живет в ее локальном `*.module.css`.
- Не возвращаться к глобальным layout-файлам для feature-страниц.

### 1.4 Чеклист перед коммитом

- `npm run -s build`
- нет ошибок линтера
- в измененных файлах нет мертвых CSS-классов/импортов
- нет legacy-импортов и неиспользуемых файлов после рефакторинга

## 2) Правила для кейсов (Case Pages)

### 2.1 Структура кейсов

- Кейсы лежат в `src/pages/CasePages/<CaseName>/<CaseName>.tsx`.
- Если у кейса есть уникальная визуальная логика, рядом создается `<CaseName>.module.css`.
- Если уникальных стилей нет, отдельный module-файл не нужен "для галочки".

### 2.2 Базовый контракт кейс-страницы

Кейс-страницы собираются из:

- `CaseHero`
- `CaseBlock`
  - `TextGroup`
  - `ImageGroup`

Цель: не строить новый layout-каркас под каждый кейс.

### 2.3 Контракт для контента и layout

- `ImageGroup`:
  - `layout="row"` — сетка в строку
  - `layout="column"` — вертикальный стек
  - `bleed` — full-width без внутренних grid-отступов
  - `fit="cover"` — только когда нужно явное кадрирование изображения
- `TextGroup`:
  - `row` — split "label/content"
  - `column` — "title + body"
  - `description` передавать как JSX с `<p>` для корректных отступов

### 2.4 Роутинг кейсов

- Lazy-импорты в `App.tsx` должны указывать на folder-based кейсы:
  - `./pages/CasePages/<CaseName>/<CaseName>`

## 3) Данные кейсов: схема, значения, нейминг

### 3.1 Где что хранить

- `src/types/case.ts` — только контракт данных (`CaseData`, `CaseCategory`).
- `src/data/cases.ts` — значения (массив `cases`) и простые helper-функции выборки.
- Компоненты импортируют:
  - типы из `src/types/*`
  - данные из `src/data/*`

### 3.2 Правила нейминга

- Имена файлов в `src/types` и `src/data` — lowercase: `case.ts`, `cases.ts`.
- Типы/интерфейсы — PascalCase: `CaseData`, `CaseCategory`.
- Коллекции — lowercase plural: `cases`.
- Не использовать похожие символы (латинская `C` vs кириллическая `С`).

### 3.3 Rename-процедура

- Любой rename делать сквозным: файл + экспорт + импорты + локальные переменные.
- После rename обязательно:
  - `npm run -s build`
  - проверка линтера
  - поиск старых имен по проекту через `rg`
